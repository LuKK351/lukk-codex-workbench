# 历史收录与完成检查

首次初始化、补录历史和恢复未完成初始化时使用。批次只是执行单位；用户选定的日期范围才是本次目标。不能把“已说明只完成首批”当作提前结束的理由。

## 先盘点，再持续处理

1. 将用户确认的起止日期和时区固定下来。读取窗口目录，按真实窗口 ID 去重，登记所有已发现候选，不只挑几个容易处理的窗口。窗口更新时间用于发现线索，最终是否纳入由消息日期决定；早年创建但近期活跃的窗口也要检查。
2. 使用工具实际支持的分页、归档列表或其他已授权来源继续发现候选。目录返回上限不是历史总量，也不是当前批次处理上限。没有目录分页能力时，登记“目录覆盖未核验”，不要猜游标或反复请求同一页。已授权本地来源可作为补充，但先检查来源结构和覆盖边界，只读取相关 Codex 记录；需要额外授权时说明具体来源与缺口。
3. 对清单中的待处理窗口逐个读取，沿返回的分页游标到授权起点或来源末尾。处理截断，保存原文证据。附图本身不在范围内，但同一消息中可读取的文字仍应保留，不能因为有图就整条丢弃。
4. 按更新流程整理、校验、发布一批，再核对发布结果并更新清单。首批网页可提前打开，作为进度展示；随后立即处理下一批，不等待用户再次发“继续”。批量大小由内容长度决定，不设置“读 3 个就结束”之类的固定交付数量。
5. 单个窗口失败时保留原因，继续其他可读窗口。工具参数错误按工具约束修正；临时错误有限重试。相同阻碍重试后没有新进展就登记阻碍，不无限重试，也不让一个失败窗口阻止其余内容收录。

## 持久进度清单

在工作台私有目录 `.workbench/history-collection.json` 保存以下字段，每批发布后更新；每次发现新窗口、读取分页或登记失败时也保存，避免发布前中断丢失进度。进度文件以临时文件写完后原子替换，避免写到一半损坏。它是恢复索引，不是发布成功的唯一证据；不放进公开仓库或网页数据。

| 字段 | 内容 |
| --- | --- |
| `version` | `1` |
| `range` | 已确认的 `start`、`end`、`timezone` |
| `status` | `in_progress`、`blocked`、`paused` 或 `complete`；只有用户明确暂停才记 `paused` |
| `discovery` | `status`（`in_progress` / `blocked` / `complete`）、来源方法、实际返回的游标、目录覆盖证据和限制；没有证据不能记 complete |
| `threads` | 按真实 ID 保存窗口标题、`status`、下一页游标、读取边界证据、来源文件、已发布批次路径及阻碍原因；另记 readThrough（已读区段/消息ID）、curatedThrough（已整理区段/消息ID）、curationStatus（pending/partial/complete）、gaps 与 exclusions，区段不能只写最新日期 |
| `updatedAt` | 本次保存时间 |
| `nextAction` | 可直接执行的下一步，明确窗口 ID、游标或待解决的来源能力 |

窗口状态使用 `pending`（未读）、`reading`、`ready`（已整理未发布）、`published`（范围内正文已读完、各目标已整理检查完且发布）、`excluded`（证据表明无范围内可收录正文）、`blocked`。部分内容已发布但仍缺页的窗口仍为 reading 或 blocked；已读完但尚有未整理内容的窗口保持 reading 且 curationStatus 为 partial，保留已发布批次信息。排除必须写原因，不能以“内容太长”或“非近期窗口”为由跳过。

`gaps` 记录待解决事项：read_error（读取失败/截断）、curation_pending（已读未整理），分别写具体区段、原因和 nextAction。`exclusions` 记录范围外内容，例如 unsupported_attachment、非讨论自动回执；按定义排除不阻塞正文整理完成。带图文字读不到仍是 read_error，不能用附件排除掩盖。清单只存进度和单批检查记录路径，不复制每项判断。

旧清单缺少整理状态或证据时视为未核验，恢复前从现有批次重建；不得把 data.json 中存在窗口当作整理完成。没有新消息也可能还有待整理内容。不要按固定目录名或数据库版本假定所有用户的来源一致。

恢复时先核对正式 data.json、published.json 与候选报告，纠正“发布成功但清单未更新”或“候选未发布”的差异。不要凭读取日志跳过未发布内容，也不要删除已发布内容重新初始化。

## 每批结束后的判断

- **还有可执行内容**：存在 pending、reading、ready，或目录还能继续发现候选，保持 in_progress，继续执行。目录受限时先处理所有已发现且可读的窗口。
- **全部完成**：目录覆盖已有证据，所有候选均为 published 或有依据的 excluded，且没有正文缺页、待拆话题、待检查事项；每窗 curationStatus 为 complete（合理排除的窗口除外）。才可记 complete，说明完成的是已核验来源中的授权范围，不能扩大为所有设备或云端历史。
- **实际阻碍**：已处理完当前能处理的内容，其余因权限、缺少读取能力或持续失败无法推进，记 blocked。说明具体阻碍、已完成量、剩余已知窗口及恢复方式；总量未知就明确未知。不能仅写“工具一次最多返回 50 条”而留下 47 个可读窗口未处理。
- **用户暂停或运行被迫中断**：先保存进度；用户暂停记 paused，运行限制中断保持 in_progress 并写明原因。不能因为上下文变长就自行判定任务完成。没有真实后台执行或已授权自动化时，不声称稍后会自动继续。

进度消息分别说明“已收录原文的窗口数、已完成整理的窗口数、仍待处理/受阻数”；存在事项整理缺口时不能用已收录窗口数计算整理完成率，目录未核验完整时再说明“历史总数尚未确定”。区分授权日期范围、实际内容日期和核验覆盖范围：最早一条消息出现在十月，并不能证明七月至九月已检查完。

完成清单前核对网页收录说明：将正式数据中的 `scopeDescription` 更新为已核验的授权范围、采集截止点及实际剩余缺口，再经候选发布。清单已完成时，网页不能仍保留“其他窗口待处理”等阶段说明；实际内容最早日期不等于授权起点。打开“收录情况”检查用户看到的说明，与最终交付一致。

首批预览、安装成功、页面验收通过都不满足历史收录完成条件。常规增量更新和定时设置不能代替本次尚可继续执行的初始化工作。

## 发布后立即选取下一步

每批发布后先更新当前窗口进度，再运行当前 Skill 目录的 `python3 <Skill>/scripts/next_step.py <工作台>`。执行返回的动作，不能只把动作写进最终答复：

- curate_or_publish：先处理已保存正文或未发布候选。
- read：使用返回的真实窗口 ID 与游标读取下一段。
- rebuild_progress / reconcile_progress：重建或修正有证据的清单，不改成 complete 来消除待办。
- verify_discovery：继续核对目录与已授权来源；目录未知不是自动停止条件。
- paused / report_blockers / complete：分别核对真实用户暂停、具体无法推进的阻碍、全部完成证据，再结束。不能为了获得 canFinish 而捏造暂停或阻碍。

准备历史收录的最终答复前运行相同命令加 `--finish-check`。退出码 2 不是运行故障，而是清单仍有工作，继续执行本轮授权范围内的动作。用户明确缩小本次更新范围时，按 update.md 分开核验本轮完成与剩余历史，不为得到 canFinish 修改历史事实。完整保留清单是恢复措施，不是提前结束的理由；“不会后台继续”“本轮结束”也不能作为停止原因。外部强制中断只能如实记录平台实际信号，不能自行决定停止后倒称“运行中断”。

这是给执行 Agent 的下一步与结束条件检查，不是后台运行器或平台停止钩子。不得承诺仅靠 Skill 就保证任意模型持续运行。验证必须包含连续多批且有剩余候选时是否真正继续，不能只用一次 release 成功代替持续执行验收。
