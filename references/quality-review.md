# 每批整理与发布检查

每批都执行，单条问答也适用。检查范围是本批消息区段及受影响事项，不要求全库每次重做。程序检查记录与引用，不代替对照原文判断。

## 先把本批做完

读取后按目标拆分/合并事情，完成小结、当日变化、决定、接续检查，再发布并处理下一批。长窗口可分段：本批只提交已完成整理的消息区段，未整理消息先保存在 sources 和进度清单，不计为完成。优先消化已读未整理区段，再扩展新窗口；单窗读取受阻不妨碍其他可读来源。不是每条消息都要变成节点：寒暄、重复与旁支可仅保留原文，但须说明其归属或不单列原因。

| 必查内容 | 完成标准 |
| --- | --- |
| 事情边界 | 识别独立目标，检查跨窗是否已有同一事情；不能只按窗口标题生成一件事。 |
| 小结与节点 | 写具体对象、问题、方案或变化；读者不打开原文也能知道讨论了什么。不能以“用户提出要求”“助手回复”“见讨论”交差。 |
| 每日变化 | 写当天实际讨论、澄清或决定，不把最终结论投射到过去。无新进展不硬编。同日同事项再次更新时，结合已收录当天节点重写当日小结，不只保留最后一批。 |
| 决定 | 明确采用、否定、限制、改选写入 decisions 并引用节点；只讨论可能性不是决定。没有明确决定时允许为空。 |
| 接续 | 对照该事项已收录的较晚消息检查继续、完成、取消证据；允许无候选。缺页影响判断时标明不确定，不能因没看到完成就认定未完成。 |

不要以决定数、任务数、小结长度作为质量指标。旧记录明确有问题时修正；程序发现可能模板句仅是警告，须判断是否真是占位，不能通过换一个泛泛同义句消除警告。

## 私有检查记录

在本批运行目录写 `quality-review.json`。先 prepare，再针对候选填写；候选或批次改变就重新核对并绑定新哈希。用 workbench.py hash 计算文件 SHA-256，禁止只复制旧记录并改哈希。

```json
{
  "version": 1,
  "candidateSha256": "候选data.json的SHA256",
  "batchSha256": "候选目录batch.json的SHA256",
  "sources": [{
    "id": "真实窗口ID",
    "messageIds": ["本批消息ID"],
    "filterNote": "按真实消息来源检查，仅保留用户正文与助手最终回复。",
    "coverageNote": "本批目标归入事项A；重复确认仅保留原文。",
    "curation": "complete"
  }],
  "items": [{
    "id": "真实事项ID",
    "evidence": [{"thread": "真实窗口ID", "messageId": "实际检查的消息ID"}],
    "boundary": "本批与既有事项的归属判断及依据",
    "summary": "检查了哪些具体变化与当前停点",
    "daily": "本批涉及日期及当日小结合并检查；无新日期也写原因",
    "decisions": {"result": "checked_none", "reason": "检查到的具体内容中未形成明确选择"},
    "continuation": {"result": "checked_none", "reason": "具体问答已回答，未提出后续目标"}
  }]
}
```

例子中的说明必须替换成实际判断，不能照抄为每件事的套话。每个判断应能追溯到 evidence 中列出的实际检查消息（包括改变状态的较晚证据）。`present` 表示候选中有该事项的决定/接续，`checked_none` 表示检查后候选中没有；历史决定保留时用 present，不能因本批无新决定就填 none。

sources 必须覆盖 batch.threads 的全部消息 ID，包括仅保留原文的消息。items 包含本批写入事项、任务、移除任务、每日小结涉及的事项，以及新写入原文所在窗口已关联的事项；即使检查后无需改动，也说明原因。这样只更新任务或只收录原文时不能漏掉对应检查。检查历史消息不意味着断言未读取来源或线下状态。

## 唯一常规发布入口

使用已验证解释器，从**当前安装 Skill** 的绝对路径运行（旧工作台不用复制新脚本，也不重建）：

```sh
python3 <Skill>/scripts/release.py <工作台> <候选目录> <批次>/quality-review.json --check-only
python3 <Skill>/scripts/release.py <工作台> <候选目录> <批次>/quality-review.json
```

check-only 后处理警告：确定是占位或事实缺陷就修改批次、重新 prepare 和复核；误报则在对应检查说明写明原因。常规发布不直接调用旧 publish 命令跳过检查。release 生成候选绑定的 quality-receipt.json，再调用既有锁定发布；成功回执在候选目录 published.json。保留该目录即可恢复。

硬阻断：候选/基线/配置变化、来源消息覆盖不全、遗漏事项检查、证据不存在/归属错误、检查未完成、决定/接续检查与候选不一致。仅警告：疑似模板表述；程序不能保证其余文本不是模板或事实正确。

旧批次重新发布需补检查记录；紧急恢复已知备份仍按 update.md 的 rollback 执行，不要求伪造旧质量记录。旧 published 回执证明曾发布，不证明已通过新检查。没有新增但旧内容尚待整理，不得当作“无需更新”。纯无新增检查无需制造候选或审查文件。
